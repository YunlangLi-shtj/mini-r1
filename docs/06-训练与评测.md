## 2. 预训练

### 2.1 怎么跑

```bash
cd /root/Test/mini-r1

bash scripts/run_pretrain.sh 1       # 参数是「用几张卡」，默认 1
bash scripts/run_watch.sh            # 守护（强烈建议，见 §2.5）
bash scripts/status.sh               # 随时查状态
```

[run_pretrain.sh](../scripts/run_pretrain.sh) 做三件事：
**① 有检查点就自动加 `--resume`**（防止误从头重跑，白烧三天）
**② 扫描 `nvidia-smi` 挑空闲卡**（两级门槛，见 [04](04-代码精读.md#c-run_pretrainsh--选卡的两级门槛)）
**③ 按卡数反推 `grad_accum`，然后用 `setsid nohup` 后台启动**

### 2.2 参数表

| 参数 | 脚本里的值 | 意思 |
|---|---|---|
| `--seq_len` | 2048 | 每条训练样本的 token 数 |
| `--micro_batch` | 1 | 每次前向几条 |
| `--grad_accum` | 由卡数反推（单卡 64） | 攒几次梯度更新一次 |
| `--peak_lr` | 3e-4 | 最高学习率 |
| `--min_lr` | 3e-5 | 退火到的最低学习率 |
| `--warmup_steps` | 500 | LR 从 0 升到峰值用多少步 |
| `--decay_frac` | 0.15 | 最后 15% 的步数用来退火 |
| `--max_tokens` | 5,000,000,000 | 总共训练多少 token（★ 见下） |
| `--ckpt_every` | 200 | 每 200 步存一次检查点 |
| `--val_every` | 200 | 每 200 步算一次验证集 loss |

**每步消耗的 token 数**（这是理解一切的钥匙）：

```
seq_len × micro_batch × grad_accum × world = 2048 × 1 × 64 × 1 = 131,072
                                                2048 × 1 × 32 × 2 = 131,072  ← 双卡，同样
```

**全局批大小固定 131k token/步**，卡多了就降 `grad_accum` 补上。
于是「换卡数」只改变**墙钟速度**，不改变**训练的动力学**（LR 节奏、数据消耗速度）
—— 这是让训练结果可复现的关键设计。

**`--max_tokens` 是唯一需要改的参数**（[run_pretrain.sh](../scripts/run_pretrain.sh) 顶部有说明）：

| 想干什么 | 怎么改 |
|---|---|
| 加练（用满 99 亿 token） | `--max_tokens 0`（0 = 跑完整数据集），LR 回到恒定段，不用重新热身 |
| 提前收尾 | 改成「当前已训 token + 约 10%」的退火尾巴，例如跑到 3.0B 时改成 `--max_tokens 3300000000` |
| 快速验证流程 | `--max_tokens 100000000`（1 亿，约 100 分钟单卡） |

**为什么「提前收尾」要加 10%**：WSD 调度会在剩余步数里退火。
如果直接把 `--max_tokens` 设成「当前 token 数」，剩余步数是 0，退火窗口也是 0，
你会停在恒定 LR 上 —— 得到一个**还没退火的半成品**。

### 2.3 日志怎么读

```
step   1200/38145 | 0.157B tok | loss 4.8123 | lr 2.90e-04 | 16,234 tok/s | 11.13G
  │        │            │            │            │              │           │
  │        │            │            │            │              │           └─ PyTorch 自报的显存峰值
  │        │            │            │            │              └─ 吞吐：每秒多少 token
  │        │            │            │            └─ 当前学习率
  │        │            │            └─ 最近 10 步的平均 loss
  │        │            └─ 已训 token 数（★ 真正的进度，它不是 step×131072 的近似，是实打实记的）
  │        └─ 总步数（5e9 / 131072 ≈ 38146）
  └─ 优化器步数（= 参数更新次数）
```

有时候会多一行：

```
  >> val loss 3.2156
```

这是**验证集**上的 loss（在没训练过的数据上算的）。它才是判断
「模型是不是真的在学，而不是在背训练数据」的依据。

**怎么判断训练正常**：

| 现象 | 含义 |
|---|---|
| loss 从 ≈11.93 起步 | ✅ 初始化正确（ln(152064) = 11.93） |
| loss 稳步下降，没有尖刺 | ✅ 正常 |
| loss 突然跳到 NaN | ❌ LR 太大 / 数据里有坏样本 / 梯度爆炸 |
| loss 卡住不动 | ❌ LR 太小，或者数据有问题 |
| **train loss 降但 val loss 升** | ❌ **过拟合**。但 5B token 对 407M 模型来说远不到过拟合，更可能是数据泄漏 |

**本项目的实测 loss 轨迹**：

```
step 100     loss ~7.x        刚开始，在学字母和常见词
step 1000    loss ~5.x        学会基本语法
step 10000   loss ~3.8        学会常识和句法
step 38141   loss ~3.1        最终，val loss 3.1296
```

### 2.4 TIP：把 loss 画成图

训练日志同时写了一份**结构化**的版本，专门给画图用：

```bash
# 从服务器拉到本地
~/.server_cmd.sh 'cat /root/Test/mini-r1/ckpts/pretrain/train_log.jsonl' > train_log.jsonl
```

每行一个 JSON：

```json

{"step": 1200, "tokens": 157286400, "val_loss": 3.2156}
```

```python
import json
import matplotlib.pyplot as plt
```

> 本项目的 [status.sh](../scripts/status.sh) 就为此写了一段很绕的 awk）。

### 2.5 守护脚本：为什么必须开

在这台共享机器上，训练被杀是**必然事件**，不是意外。守护脚本
[watch_pretrain.sh](../scripts/watch_pretrain.sh) 的逻辑：

```
每 60 秒检查
  ├─ 训练进程还在？ → 继续等
  └─ 不在了 →
       ├─ 日志里（本次启动之后）有"训练完成"？ → 正常结束，守护退出
       └─ 没有 → 重新选卡 → bash run_pretrain.sh（自动 --resume）
```

**实测效果**：预训练**连跑 46 小时零重启**，守护脚本按设计在训练完成后自己退出了。
这不是运气好，是 [run_pretrain.sh](../scripts/run_pretrain.sh) +
[watch_pretrain.sh](../scripts/watch_pretrain.sh) +
[train_pretrain.py](../src/train_pretrain.py) 的断点续训三者配合的结果。

**怎么知道守护在不在跑**：

```bash
~/.server_cmd.sh 'cd /root/Test/mini-r1 && bash scripts/status.sh'
# 输出里会有「守护进程: 在跑」或「⚠️ 不在跑」
```

## 3. SFT

### 3.1 怎么跑

```bash
bash scripts/run_sft.sh          # 有 ckpts/sft/sft_latest.pt 就自动续训
bash scripts/watch_sft.sh        # 守护
```

### 3.2 参数表

| 参数 | 值 | 为什么 |
|---|---|---|
| `--max_samples` | 200000 | 20 万条对话（数据集有 100 万条） |
| `--max_len` | 2048 | 最长 2048 token，超出截断 |
| `--micro_batch` | 1 | ★ 见下 |
| `--grad_accum` | 32 | 1 × 32 = 32 条/步 |
| `--grad_ckpt` | 1 | 梯度检查点 |
| `--lr` | 2e-5 | 比预训练小一个数量级（微调不能大改权重） |
| `--epochs` | 1 | 过一遍就够 |
| `--ckpt_every` | 100 | 每 100 步存一次（约 7 分钟） |
| `--seed` | 1234 | ★ 续训必须一致 |

**为什么 `--micro_batch 1`**：这不是随便选的，是三次 OOM 换来的。

| 档位 | 峰值显存 | 结论 |
|---|---|---|
| mb8（原默认） | 首次前向就 OOM（16.03 GiB） | 废弃 |
| mb4 + grad_ckpt | 反向时 OOM（爬到 24.35 GB，**比 mb8 还费**） | 废弃 |
| **mb1 + grad_ckpt** | **9.81 GB** | ✅ 当前选择 |
| mb2 + grad_ckpt | ~12.2 GB | 可行但要等更干净的卡，快一倍 |

「mb4 比 mb8 还费」这件事很反直觉 —— 它说明**显存模型靠估算是不可靠的**，
只能实测（[probe_sft.sh](../scripts/probe_sft.sh) 就是干这个的）。
根因是 SFT 每条样本平均只有约 358 个有效 token，
**小批次的固定开销占大头**，而梯度检查点的重算策略又和批次大小有非线性关系。

**为什么全局批固定 32 条**：和预训练同一个道理 ——
`mb1 × ga32` 和 `mb2 × ga16` 消耗的数据一样多、LR 节奏一样，
换档位只改墙钟速度。**但注意：换档位会破坏续训**（见下）。

### 3.3 ⚠️ 续训的硬约束

> **续训只认 `seed + micro_batch + grad_accum` 完全一致的组合。**
> 换了这三个里的任何一个，就必须**删掉 `sft_latest.pt` 从头跑**。

原因见 [04-代码精读](04-代码精读.md#c-续训三个必须一致的东西)：
续训实现是「固定 seed 重现 shuffle 顺序 → 空转跳过已消费的 micro-batch」。
换了 `micro_batch`，一个 micro-batch 装的是**不同的样本组合**；
换了 `seed`，shuffle 顺序整体不同 —— 两种情况都会跳到**错误的数据位置**上，
而且**不报任何错**。

**本项目有一次真实的验证**：2026-10-12 下午服务器关机装硬盘，
16:12 重启后守护脚本自动拉起，日志显示：

```
===== [10-12 16:15] 启动 SFT (GPU 0) =====
★ 从 SFT 检查点续训: 已完成 1000/6240 步 (已消费 32,000 个 micro-batch)
```

**从检查点无损接着跑，人工零干预。**

## 4. GRPO

### 4.1 依赖：KV-Cache（已完成，4.78×）

[model.generate()](../src/model.py#L276) **默认带 KV-Cache**（`use_cache=True`），
GRPO 的 rollout 白拿这个加速。实测（[bench_kv_cache.py](../scripts/bench_kv_cache.py)，真实 407M、fp32）：

| | 每组 rollout | 吞吐 | 300 步 GRPO |
|---|---|---|---|
| 无缓存 | 24.96 s | 123 tok/s | 49.9 小时 |
| 有缓存 | 5.22 s | 589 tok/s | **10.4 小时** |

原理和三个坑（其中两个"不报错但算错"）见 [04-代码精读](04-代码精读.md) ①(d)。

**跑之前先过这一关**（纯 CPU，10 秒）：

```bash
CUDA_VISIBLE_DEVICES="" python scripts/test_kv_cache.py
```

### 4.1′ ⚠️ 更要紧的：基座在 GSM8K 上是 0 分

**先看实测数字**（2026-10-13，SFT 基座 = 20 万条 OpenHermes 训完）：

| 指标 | 实测 |
|---|---|
| pass@1 | **0.0**（20 题一条都不对） |
| 每条回答的准确率 | 约 0.2% ~ 0.6% |
| 格式正确率（用了 `\boxed{}`） | **0.55** |

**原因不是 bug**：OpenHermes 里几乎没有数学思维链，模型没见过
「先一步一步推、最后把答案放进 `\boxed{}`」这个样板。
它已经学会**照着格式写**（0.55），但**不会算**。

**这意味着 GRPO 能学到的信号，主要是那 0.1 分的格式奖励**（见 §4.3 的「有信号组」）。
想拿到准确率上的提升，需要先加一段 GSM8K-CoT 的 SFT 热身（约 16 分钟）。
完整的分析和两条路线见 [AGENTS.md](../AGENTS.md) §8 第 1 条。

**后来真的跑完 300 步 GRPO，结论比这里预判的还要糟** —— 见 §4.1″。

### 4.1″ ⚠️ 第一次跑完的真实结果：那 0.1 分被 hack 了

上面预测「GRPO 主要会去学格式分」。300 步跑完后，**格式分确实吃满了，但不是学会了格式**。

#### 发生了什么

`format_reward` 只看输出里**有没有 `\boxed{` 这个子串**：

```python
def format_reward(completion):
    return 0.1 if re.search(r"\\boxed\{", completion) else 0.0
```

而提问模板 `PROMPT_TMPL` 里正好**原样印着** `\boxed{...}` 这个占位符：

```
... Please reason step by step, and put your final answer within \boxed{...}.
```

于是拿到那 0.1 分最省力的办法，不是去解题，而是**把提示词里的占位符抄一遍**。
模型选了后者：

| | SFT 基座 | GRPO 跑完 |
|---|---|---|
| 输出里含 `\boxed{` | 4.7% | **66%** |
| 其中是字面量 `\boxed{...}`（照抄占位符），不是真答案 | — | **100%** |
| 贪心输出含 `\boxed{` | 0/256 | 42/256 |
| 这 42 条里有几条是真答案 | — | **0 条** |

原始输出长这样（`scripts/show_completions.py` 打印的，未经过 `extract_answer`）：

```
4. cannot be true within \boxed{...}
5.
```

#### 为什么日志上一点都看不出来

**每个指标都在变好**，而且是「刚刚好」地变好：

| 日志上的数 | 看起来 | 实际 |
|---|---|---|
| `r` 0.0549 → 0.0976 | 奖励在涨 | **逼近 0.1 的格式分上限** —— 它涨的就是那 0.1 |
| 格式正确率 → 1.00 | 格式学会了 | 学会的是抄占位符 |
| 贪心 `pass@1` 0 → 0.0156 | 准确率起来了 | 4/256，**在噪声内**（σ≈1.6 题） |
| `有信号组` 17.2 → 7.3 | 只是变难了 | **奖励越来越同质** —— 所有组都拿了同样的 0.1 |

**`r` 的上限是 0.1**（数学分是 0），所以 `r → 0.099` 不是「快满分了」，
而是「已经把能拿的唯一一分拿完了」。这个数字在日志里看着像进步，实际是天花板。

#### 三条能带走的经验

1. **规则里用到的字符串，绝不能同时出现在提示词里。**
   哪怕只是个占位符。这不是「模型太笨看不懂 `...`」，而是**奖励函数是自己发的邀请函**。
2. **奖励函数必须惩罚「拿到了格式但没给答案」。** 光改成
   `\boxed{([^{}]*)}` 还不够 —— 得**检查括号里真的有东西、且不是 `...`**：

   ```python
   m = re.findall(r"\\boxed\{([^{}]*)\}", completion)
   ok = any(normalize(x) not in (None, "", "...", "…") for x in m)
   return 0.1 if ok else 0.0
   ```

   同时把模板改成不含可抄字面量的写法（比如 `put your final answer within a
   \boxed{} block` 这种不带省略号的措辞，或者干脆不说 `\boxed`，只在评分里认它）。
3. **在一个错误的指标上做出统计显著，比不做统计更危险。**
   训练日志的 pass@1 序列涨得是有统计意义的（置换检验 P≈0.4%），
   但那个序列量的是**贪心口径**——**正是掩盖了这次退化的那一个口径**。
   换评测口径（`temperature=1.0`、8 条取第 1 条）后，GRPO 的 pass@1 是 **0.0**。

#### 和「基座太弱」的关系

两件事**同时成立、但成因不同**：

- 基座弱（pass@1=0）→ GRPO **学不会做题**（没有正样本可强化）；
- 奖励可抄（提示词里有 `\boxed{...}`）→ GRPO **学会抄占位符**（这个它一学就会）。

前者是数据问题（要补 GSM8K-CoT 热身），后者是**代码问题**（要先修奖励函数）。
顺序不能反：**不修奖励就补热身，只会让模型抄得更起劲。**

### 4.2 参数表

| 参数 | 值 | 意思 |
|---|---|---|
| `--G` | 8 | 每道题采样几条回答（组内相对优势的分母） |
| `--rollout_batch` | 24 | 每步用几道题 |
| `--max_new` | 384 | 每条回答最多生成多少 token |
| `--temperature` | 1.0 | 采样温度（要探索，所以不用贪心） |
| `--beta` | 0.04 | KL 惩罚系数（越大越保守） |
| `--clip_eps` | 0.2 | 概率比的裁剪范围 [0.8, 1.2] |
| `--update_epochs` | 2 | 同一批数据重复更新几轮 |
| `--lr` | 5e-6 | 比 SFT 再小一个数量级 |
| `--max_steps` | 300 | 总共 300 步 |
| `--ckpt_every` | 5 | 每 5 步写一次 `grpo_latest.pt`（续训用） |
| `--eval_every` | 25 | 每 25 步评测一次并写 `grpo.pt` |

**实测**：一步约 148 秒、峰值显存 **14.0 GiB**（PyTorch 口径；驱动器按 17.3 GiB 记账，
`run_grpo.sh` 因此要 **19000 MiB** 空闲）。

**续训**：`run_grpo.sh` 会自动检测 `ckpts/grpo/grpo_latest.pt` 并接上，
不用加参数。超参改了会在日志里警告（改了 `--G`/`--beta` 这类仍然「能」续上，
但那是在混两个实验，自己确认）。

### 4.3 日志怎么读

```

  │          │            │           │                 │           │       └─ ★ 本步峰值显存
  │          │            │           │                 │           └─ 累计墙钟（秒）
  │          │            │           │                 └─ 当前 LR
  │          │            │           └─ ★ 24 道题里有多少道组内奖励有差异
  │          │            └─ 原始奖励均值（答对 1.0 + 格式 0.1）
  │          └─ 策略损失（可正可负，看趋势不看绝对值）
  └─ 步数

  >> GSM8K pass@1 = 0.0117      ← 每 25 步评测一次，这才是真正关心的数字
```

**为什么不用 `avg_r`（平均优势）当指标**：优势是 `(r - 组内均值) / 组内标准差`，
**组内均值恒等于 0** —— 拿它当指标等于每步都打印 0，什么也看不出来。
（第一版就是这么写的。）

**「有信号组」才是该盯的数**：

| 组内 8 条奖励 | std | 这组数据 |
|---|---|---|
| 全对 / 全错 | 0 | **白采**，优势全是 0，没有学习信号 |
| 3 对 5 错 | >0 | ✅ 有用 |

**它接近 0 就说明奖励设计或 `max_new` 有问题，别干等 300 步** ——
项目里就真踩过一次（奖励函数恒返回 0，现象正是 `有信号组 0/1`，
见 [04-代码精读](04-代码精读.md) ⑥(a′)）。

**该盯什么**：

| 指标 | 期望 | 不正常的信号 |
|---|---|---|
| `pass@1`（每 25 步） | 随步数上升 | 一直不涨且 `有信号组` 也接近 0 → **先查奖励函数**，再查 LR |
| `有信号组` | 冷启动期 ~50%，之后上升 | 恒为 0 → 奖励函数坏了（拿标准答案喂进去自测，见 §4.4） |
| `r`（原始奖励） | 缓慢上升 | 一直 0.0000 → 同上；**卡在某个整数上限附近 → 多半是奖励被 hack 了**（§4.1″） |
| `loss` | 在 0 附近波动 | 一直增大 → KL 惩罚不够，模型跑偏了 |
| ~~格式正确率~~ | ⚠️ **别单独看这一项** | 涨到 1.00 **不代表学会了格式** —— 本项目实测就是「1.00 = 全在抄提示词里的占位符」（§4.1″） |
| 每步耗时 | 约 148 s（KV-Cache 后） | 远大于此 → 缓存没生效 |
| `峰值` | 13~14 G | **超过 21 G → 快 OOM 了**，别等它崩（[08-Q3′](08-排错FAQ.md)） |

> ⚠️ **这张表本身误导过一次，所以划掉了「格式正确率」那一行。**
> 它当时写着「应快速接近 1」，而真实结果里它确实到了 1.00 —— **照着这张表看，
> 那次很糟的训练看起来完美达标**。教训：**日志里的数字全是"代理指标"，
> 代理指标涨不代表目标变好，一定要有一步是看原始输出。**
> `scripts/show_completions.py` 就是为这一步准备的（打印未解码的原文）。

### 4.4 跑之前必须过的自检

```bash
python -c "
import sys; sys.path.insert(0, 'src')
from train_grpo import load_gsm8k
load_gsm8k('tokenizer/tokenizer.json', gsm8k_dir='data/raw/gsm8k')
"
```

会打印 `奖励函数自检: 200 条标准答案全部判对 ✓`。
**不打印这行就不算过**（`load_gsm8k` 里的 `check_reward_fn` 会直接 assert 失败）。

这个自检是**被现实教出来的**：GSM8K 的 `answer` 字段是整段解题过程，
答案在最后一行 `#### 72`。原来的代码拿整段去跟模型输出的 `"72"` 比 ——
**奖励恒为 0，训练时权重纹丝不动、评测时 pass@1 恒为 0，且不报任何错。**

## 5. 显存账本（这一节能省你几个小时）

### 5.1 三个数字，别搞混

训练时你会看到三个不同的「显存占用」，**它们不是一回事**：

| 数字 | 来源 | 预训练实测 | SFT 实测 | GRPO 实测 |
|---|---|---|---|---|
| `max_memory_reserved` | [probe_mem.py](../scripts/probe_mem.py) 报告 | 8.19 GiB | — | — |
| `max_memory_allocated` | 训练日志里的 `11.13G` / `9.91G` / `峰值 14.0G` | 11.13 G | 9.81~10.17 G | **14.0 G** |
| **驱动器口径** | `nvidia-smi` 真正记账的 | **12,046 MiB** | **~10,850 MiB** | **17,718 MiB** |

（最后那一列 GRPO 的差距最大：PyTorch 自报 14.0 GiB，驱动器按 **17.7 GB** 记账 ——
差 3.7 GB。所以门槛要按 17.7 那一列算，不能按日志里那个 14.0。
`run_grpo.sh` 的门槛就是这么从 16000 提到 **19000** 的：16000 只保 15.6 GiB，
真在这样一张卡上起来照样 OOM。

> 💡 **一次 `nvidia-smi` 看到的就是峰值**：GRPO 进程连采 44 次 `memory.used`
> （跨了整整一个 step）**全是 17,726 MiB，一次没变** —— 因为 `expandable_segments:True`
> 的池子涨上去就不还给驱动器了。所以这个数是**高水位线**而不是瞬时值，
> 随手看一眼就够，不用盯着采样。）

**差在哪**：PyTorch 报的是「我向 CUDA 申请了多少」，
而驱动器还要算上 **CUDA 上下文**（约 300~500 MB）、
**显存碎片**、**分配器缓存**。

**结论**：

> **选卡的门槛必须按 `nvidia-smi` 口径设，不能信 PyTorch 的自报数。**

按 8.19 或 11.13 设门槛 → 选中「看起来够」的卡 → 一启动就 OOM →
守护脚本重试 → 又选中同一张卡 → **永远起不来**。

本项目踩过这个坑：门槛原来是 11800 MiB，
**卡在 12,046 这条线下面**，会选中装不下的卡。
现在 [run_pretrain.sh](../scripts/run_pretrain.sh) 用的是 **13000**。

顺带一提：`max_memory_allocated` 在配置完全相同的情况下，
历史上报过 8.19 / 9.61 / 11.13 **三个不同的值**，原因未查明。
所以**绝对不能拿它当门槛依据**。真要看占用，用：

```bash
nvidia-smi --query-compute-apps=pid,used_memory --format=csv
```

### 5.2 显存都花在哪了

以 407M 模型、bf16 训练为例：

| 项 | 大小 | 说明 |
|---|---|---|
| 模型权重（bf16） | 0.8 GB | 407M × 2 字节 |
| 梯度（bf16） | 0.8 GB | 和权重一样大 |
| **AdamW 优化器状态（fp32）** | **3.3 GB** | ★ 每个参数两个 fp32 状态 = 407M × 8 字节 |
| 激活值 | ~2 GB | 开梯度检查点后大幅降低 |
| **LM head + 交叉熵临时张量** | **0.3~1.2 GB** | ★ 见下 |
| DDP 梯度桶（多卡） | +1.5 GB/卡 | 单卡不需要 |

**两个"意外"的大头**：

- **优化器状态比模型大 4 倍**。这是很多人第一次训练时想不到的，
  也是为什么「续训检查点 4.9 GB，而最终模型只有 1.6 GB」。
- **152k 词表的输出层**。这就是 [chunked_cross_entropy](../src/model.py#L44)
  存在的理由 —— 见 [04-代码精读](04-代码精读.md#b-分块交叉熵为什么它是最重要的一个优化)。

**想省显存，按性价比排序**：梯度检查点 → 分块交叉熵 → 降 micro_batch
→ 优化器状态换 8-bit（`bitsandbytes`）→ ZeRO / FSDP。

### 5.3 GRPO 的账本（fp32，21 GiB → 14 GiB）

GRPO 是**唯一一个 fp32 跑的阶段**（要算概率比和 KL，bf16 的精度不够），
所以同样的模型占的显存比预训练/SFT 大得多。
第一次跑起来时进程占 **21.28 GiB 还在涨**，要 2.52 GiB 拿不出来，连崩 78 次：

| 项 | 大小 | 怎么来的 |
|---|---|---|
| 策略模型权重（fp32） | 1.63 GB | 407M × 4 字节 |
| 参考模型权重（fp32） | 1.63 GB | π_ref，冻结，**必须常驻**（每步都要算 KL） |
| AdamW 两个动量（fp32） | 3.26 GB | 只给策略模型 |
| 梯度（fp32） | 1.63 GB | 只给策略模型 |
| logits（G=8 × T≈500 × 152k 词表） | 2.43 GB | `F.linear` 的输出 |
| `log_softmax` 的输出 | 2.43 GB | 反传需要它，**和上一条同时活着** |
| **16 层激活（没开梯度检查点时）** | **~5 GB** | ★ 修掉它和下面那条就够了 |
| ~~`ckpt`（SFT 基座）~~ | ~~1.63 GB~~ | ★ **泄漏**：`load_state_dict` 是复制，原件没释放 |
| ~~`ck`（grpo_latest.pt）~~ | ~~4.90 GB~~ | ★ **同样泄漏**（权重 1.63 + 优化器 3.26） |

后两行加起来 **6.5 GB 是纯垃圾** —— `torch.load(..., map_location=device)` 让张量
直接落在 GPU 上，而 `load_state_dict` 把它们**复制**进参数后，原件只要还被变量引用着
就一直在。修法是 `map_location="cpu"` + `del`，故事见
[docs/04 ⑥(f)](04-代码精读.md) 和 [08-Q3′](08-排错FAQ.md)。

修完 **峰值 14.0 GiB**，一步 148 秒（原来 146 秒 —— 开梯度检查点的重算开销
落在噪声里，因为时间大头是 rollout 采样，不是更新）。

> ⚠️ **fp32 的 logits 是隐藏的大头**：`8 × 500 × 152064 × 4 字节 = 2.43 GB`，
> 而 `log_softmax` 还要再开一份同样大的。词表越大、`G × max_new` 越大，这两条涨得越快。
> 真要在小卡上跑 GRPO，先把 `G` 或 `max_new` 降下来，比调别的都管用。

## 6. 检查点

### 6.1 两种检查点，用途不同

| 文件 | 内容 | 大小 | 用途 |
|---|---|---|---|
| `*_latest.pt` | model + **optimizer** + 进度 | 4.9 GB | **续训** |
| `sft.pt` / `grpo.pt` | **只有 model** | 1.6 GB | 推理 / 下一阶段 / 评测 |

**为什么续训版大 3 倍**：AdamW 要为每个参数保存两个 fp32 状态
（一阶动量 m、二阶动量 v），合计 8 字节/参数 —— 是 bf16 权重的 4 倍。

**为什么一定要存优化器状态**：只恢复权重的话，动量从 0 重新开始，
续训后头几百步会明显抖动（相当于「刚热身完又冷下来」）。

### 6.2 自己读一个检查点

```python
import torch
c = torch.load("ckpts/sft/sft_latest.pt", map_location="cpu")

print(list(c.keys()))       # ['step', 'micro', 'model', 'opt']
print("step:", c["step"])   # 3500
print("micro:", c["micro"]) # 112000
print("模型张量数:", len(c["model"]))     # 146
print("优化器状态数:", len(c["opt"]["state"]))  # 146（每个参数一组 m/v）
```

> ⚠️ **PyTorch 2.6 起 `torch.load` 默认 `weights_only=True`**：
> 只允许加载「纯张量 + 基本类型」，防止恶意检查点执行任意代码。
> 本项目的检查点是 `dict{str: int|dict[str: tensor]}`，符合要求。
> 如果你往检查点里塞了自定义对象（比如 `ModelConfig()` 实例），加载会失败。

### 6.3 检查点策略：频率是个权衡

| 项目 | 值 | 说明 |
|---|---|---|
| 预训练 `--ckpt_every` | 200 步 | ≈ 45 分钟；检查点 4.9 GB |
| SFT `--ckpt_every` | 100 步 | ≈ 7 分钟；写盘约 30 秒 |

**SFT 为什么更频繁**：SFT 全程只有 7 小时，写盘开销占比约 7%。
换来的是「被抢占最多丢 7 分钟」。
预训练 200 步一次是因为它要跑好几天，写盘太频繁会明显拖慢。

**通用公式**：检查点间隔 ≈ 「你能接受的损失」。
被中断时损失的进度 = 一个检查点间隔。

## 7. 评测

```bash
bash scripts/run_eval.sh <检查点路径> <标签> [题目数]
# 例：
bash scripts/run_eval.sh /root/Test/mini-r1/ckpts/sft/sft.pt sft 256
```

跑完产出 `reports/gsm8k_sft.json`：

```json
{
  "result": {
    "ckpt": ".../sft.pt", "n": 256, "n_samples": 8, "temperature": 1.0,
    "pass@1": 0.xxxx,
    "maj@8": 0.xxxx,
    "format_ratio": 0.xxxx
  },
  "details": [ { "q": "Janet's ducks lay 16 eggs...", "gold": "18",
                 "answers": ["18","18","20",null,...], "correct": true }, ... ]
}
```

`details` 字段很有用 —— 能直接看到模型在哪类题上错、错成了什么。

### 7.1 核心消融实验

**这是简历上最重要的数字**：同一个测试集，两个模型各跑一次。

```bash
# ① SFT 模型（GRPO 之前）
bash scripts/run_eval.sh /root/Test/mini-r1/ckpts/sft/sft.pt sft

# ② GRPO 模型（GRPO 之后）
bash scripts/run_eval.sh /root/Test/mini-r1/ckpts/grpo/grpo.pt grpo
```

**对比表**（2026-10-14 实测，256 题，同一份测试集、同样参数）：

| 模型 | pass@1 | maj@8 | 格式正确率 | pass@1（贪心口径） |
|---|---|---|---|---|
| base（预训练） | — | — | — | — |
| SFT | 0.0078（2/256） | 0.0078 | 0.426 | 0.0000（0/256） |
| + GRPO | **0.0000（0/256）** | **0.0000** | **1.000** | 0.0156（4/256） |

**怎么读这张表**（⚠️ 别只念数字）：

- **准确率上没有任何可测的变化。** 0/256 vs 2/256、0/256 vs 4/256 ——
  p≈0.01 时 256 题的 σ ≈ 1.6 题，**这几个差值全在噪声里**。
  能说的只有「**没有证据表明 GRPO 提升了准确率**」，不能说「GRPO 让准确率下降了」。
- **格式正确率 0.426 → 1.000 是这次唯一巨大的、可复现的效应 —— 但它是个 hack。**
  涨的那部分全是「照抄提示词里的 `\boxed{...}` 占位符」，机制见 §4.1″。
- **两个口径给出相反的排序**：采样口径 SFT 赢（0.0078 vs 0），
  贪心口径 GRPO 赢（0 vs 0.0156）。**在噪声里挑口径 = 自欺欺人**，
  正确结论是「两者没有差别」。

**⚠️ 评测的四个坑**（第 4 条是这次新踩的）：

1. **必须用同一份测试集、同样的采样参数**。`n_samples`、`temperature`、
   `max_new` 任何一个不同，数字就不可比。
2. **样本量要够**。256 题上 1% 的差异是噪声，要报就报全量 1319 题。
3. **不要拿 loss 跨阶段比较**（见 [01](01-项目全貌与术语.md#35-评测相关)）。
4. **⚠️ 同名不同义的指标会给出相反的结论。** 本项目里
   「pass@1」有**两个**实现：

   | 出处 | 口径 | 谁在用 |
   |---|---|---|
   | `train_grpo.eval_pass1` | **贪心**（temperature=0），1 条 | 训练日志每 25 步 |
   | `eval_gsm8k.py` | temperature=1.0，8 条里取**第 1 条** | `run_eval.sh` |

   名字一样、数字差一个数量级、**排序还相反**。摆在一起对比必然得出错误结论。
   对齐口径用 `scripts/eval_greedy.py`：

   ```bash
   python scripts/eval_greedy.py /root/Test/mini-r1/ckpts/grpo/grpo.pt 256
   ```

   它走的是 `train_grpo.eval_pass1` **同一条代码路径**（不是重写一遍），
   顺带统计字面量 `\boxed{...}` 的条数 —— 就是上面那张表最后一列和 hack 的证据。

### 7.2 可选的消融

[AGENTS.md](../AGENTS.md) §8 列了可以做的消融：
G 的大小（4/8/16）、β（0 / 0.04 / 0.1）、clip ε、奖励设计（去掉格式奖励）、
`update_epochs`（1 / 2 / 4）。这些能体现「知道每个超参在干什么」，
是面试时的加分项。

**已经白捡了一个对照组**：这一次 300 步的 GRPO 直接从 OpenHermes-SFT 基座起跑
（pass@1 = 0，见 §4.1′），而且**奖励函数是坏的**（§4.1″）。
修好奖励、补上 GSM8K-CoT 热身再跑一遍之后，这一次正好当**对照组**：
「**坏奖励 vs 好奖励**」和「**不热身 vs 热身**」各是一张表。

后一张表特别有说服力 —— 它说明 **GRPO 不是魔法：它只能把基座里已有的能力放大，
不能无中生有**。这一次的实测就是这句话的证据：基座做对率 0.2%，
GRPO 强化不了它没有的能力，于是只学走了那个白送的 0.1 分。

## 9. 新手常见疑问

**Q：跑一次预训练要 3.5 天，我这三天能干什么？**
A：什么都不能干 —— 但也不需要你干什么。`setsid nohup` 让它脱离终端，
守护脚本负责在它被杀时拉起来。你可以关电脑、断网、睡觉。
**唯一要避免的是手动 `kill` 它**。

**Q：能不能先跑个小的看看？**
A：可以，而且应该。

```bash
python scripts/make_smoke_data.py /tmp/smoke        # 造 500 万随机 token 的假数据
python src/train_pretrain.py --data_dir /tmp/smoke --ckpt_dir /tmp/smoke_ckpt \
    --micro_batch 2 --grad_accum 2 --max_tokens 2000000
```

**Q：loss 降到多少才算好？**
A：没有绝对标准，看趋势。对 407M 模型 + 5B token，
val loss 落在 3.0~3.3 是正常的。**重要的不是绝对值，而是
「和 baseline 比有没有变好」** —— 而 baseline 就是你自己。

**Q：为什么我的 loss 和论文里对不上？**
A：**loss 不可跨模型/跨数据/跨配置比较**。
词表大小不同、数据不同、算 loss 的位置不同，数字就没有可比性。
可比的是同一套配置下的相对变化。
