## 1. 仓库里为什么没有数据

```bash
$ du -sh data/ ckpts/ miniforge/
 29G  data/raw/      # 原始下载的 parquet / json
 37G  data/train/    # 分好词的 token 分片
 15G  ckpts/         # 模型检查点
  7G  miniforge/     # conda 环境
```

**加起来约 88 GB**，而 GitHub 单文件限制 100 MB、单仓库建议不超过 1 GB。
更重要的是：**这些全部可以由代码重新生成** ——
数据集是公开的，分片是 [data_pretrain.py](../src/data_pretrain.py) 跑出来的，
模型是训练出来的。把可再生产物塞进版本控制是反模式。

所以 [.gitignore](../.gitignore) 把它们全部排除了。详见 [07-GitHub与工程实践](07-GitHub与工程实践.md)。

> 想直接看**训练好的模型**？见 [AGENTS.md](../AGENTS.md) §8 的「未来工作」——
> 上传 HuggingFace 是待办事项。

## 2. 三个数据集

| 阶段 | 数据集 | 是什么 | 大小 | 许可 |
|---|---|---|---|---|
| 分词器 + 预训练 | **FineWeb-Edu** (sample-10BT) | 从 CommonCrawl 里筛出来的**教育类**网页文本，用一个小模型给每页打「教育价值」分，只留高分页 | 14 个 parquet，29 GB | ODC-By 1.0 |
| SFT | **OpenHermes-2.5** | 100 万条**对话数据**（用户提问 + 助手回答），由 GPT-4 等模型生成/整理 | 1.9 GB json | Apache-2.0 |
| GRPO + 评测 | **GSM8K** | 8500 道**小学数学应用题**，带完整解题步骤 | 2.7 MB parquet | MIT |

**为什么预训练用 FineWeb-Edu 而不是原始 CommonCrawl**：
原始网页里充斥着广告、导航栏、乱码。数据质量对预训练的影响**比模型结构还大** ——
这也是近两年的共识（「数据比架构重要」）。FineWeb-Edu 是 HuggingFace 用分类器筛过的版本，
是当前小模型预训练的事实标准之一。

**为什么 SFT 只要 20 万条**（数据集有 100 万条）：
SFT 是「教格式」，不是「灌知识」。20 万条已经足够让模型学会对话格式，
再多收益递减，而显存和时间是实打实的成本。
（[run_sft.sh](../scripts/run_sft.sh) 里 `--max_samples 200000`。）

**GSM8K 为什么这么小还能当基准**：它衡量的是**推理能力**，不是知识量。
1319 道测试题都是「小明有 5 个苹果……」这种，需要多步计算。
模型不可能靠背答案过 —— 这是个设计得很干净的基准。

## 3. 为什么不用 `datasets` 直接下载

理论上，一行代码就能下载：

```python
from datasets import load_dataset
ds = load_dataset("HuggingFaceFW/fineweb-edu", "sample-10BT")
```

**实际会崩。** 原因链：

```
① 国内直连 huggingface.co 不通 → 必须走镜像 hf-mirror.com
② datasets 库通过 HF_ENDPOINT 环境变量走镜像 ✅
③ 但 hf-mirror 的**部分 tree API 请求会 302 跳回 huggingface.co** ❌
④ datasets 会跟随重定向 → 请求发到被墙的域名 → 超时/连接重置 → 崩
```

**解法：用 `curl` 把文件直接下到本地，再读本地文件。**

```python
ds = load_dataset("parquet", data_files=["/root/Test/mini-r1/data/raw/000_00000.parquet"], split="train")
```

这样完全不碰数据集枚举 API，规避了整个问题。

### 3.1 下载脚本

[scripts/download_data.sh](../scripts/download_data.sh)：

```bash
REV=87f09149ef4734204d70ed1d046ddc9ca3f2b8f9
BASE="https://hf-mirror.com/datasets/HuggingFaceFW/fineweb-edu/resolve/$REV/sample/10BT"

curl -sL -C - --retry 10 --retry-delay 3 --connect-timeout 20 \
  --max-time 600 --speed-time 60 --speed-limit 1024 \
  -o "$f.part" "$BASE/$f" && mv "$f.part" "$f"
```

每个参数都是在解决一个具体的失败模式：

| 参数 | 解决什么 |
|---|---|
| `-C -` | **断点续传**。29 GB 的下载中断是常态，不能每次都从头 |
| `--retry 10 --retry-delay 3` | 网络抖动自动重试 |
| `--max-time 600` | 单次尝试最多 10 分钟，卡死了就重来 |
| `--speed-time 60 --speed-limit 1024` | 60 秒平均速度低于 1 KB/s 就判定为卡死，断开重试 |
| `-o "$f.part"` + `mv` | 先写到 `.part`，**下完了才改名**。这样「存在 `$f`」就等于「完整」 |
| `REV=<commit hash>` | 钉死数据集版本，避免上游更新导致复现不一致 |

### 3.2 一个必须防的并发 bug

```bash
exec 9>/tmp/.mini_r1_download.lock
flock -n 9 || { echo "已有下载实例在跑, 退出"; exit 1; }
```

**如果两个下载进程同时对同一个文件 `-C -` 续传**，
它们会**各自从断点开始写，交错覆盖**同一段字节 —— 结果是一个
**看起来大小正常、但内容损坏**的 parquet。`datasets` 读它时才报错，
而那时你已经浪费了几小时。

`flock`（文件锁）保证同一时刻只有一个下载实例。

> 📌 有意思的对照：**守护脚本**反而不能用 `flock`（见
> [04-代码精读](04-代码精读.md#b-watch_pretrainsh--watch_sftsh--守护脚本)），
> 因为 flock 的 fd 会被 `sleep` 子进程继承。**同一个工具，在两个场景下一次对一次错** ——
> 用之前要想清楚它的语义。

[scripts/download_aux.sh](../scripts/download_aux.sh) 用同样的模式下载
GSM8K 和 OpenHermes（体积小，逻辑更简单）。

## 4. 全流程：从原始文本到训练分片

```bash
cd /root/Test/mini-r1

# ① 下载（约 1~2 小时，看网速；可重复执行，已存在的会跳过）
bash scripts/download_data.sh
bash scripts/download_aux.sh

# ② 训分词器（约 20 分钟，只用 2 亿字符）
miniforge/envs/mini-r1/bin/python src/tokenizer_train.py \
    --local_dir data/raw --out_dir tokenizer
# 产物: tokenizer/tokenizer.json (11 MB)

# ③ 分词 + 分片（约 1~2 小时）
miniforge/envs/mini-r1/bin/python src/data_pretrain.py \
    --local_dir data/raw \
    --tokenizer tokenizer/tokenizer.json \
    --out_dir data
# 产物: data/train/shard_00000.bin ... shard_00099.bin + data/val.bin
```

**顺序不能变**：③ 依赖 ② 产出的分词器，② 依赖 ① 下载的文本。

③ 支持断点续跑，因为中途可能被打断：

```bash
--skip_files N     # 跳过前 N 个 parquet（已产出分片的那些）
```

分片编号会**自动接着已有的排**（[data_pretrain.py L98](../src/data_pretrain.py#L98)）：

```python
start_idx = len(glob.glob(f"{args.out_dir}/train/shard_*.bin"))
```

## 5. 产物长什么样

```
data/
├── raw/                          # 29 GB：原始下载
│   ├── 000_00000.parquet         #   FineWeb-Edu，14 个
│   ├── ... 013_00000.parquet
│   ├── gsm8k/
│   │   ├── train.parquet         #   7473 题
│   │   └── test.parquet          #   1319 题
│   └── openhermes/
│       └── openhermes2_5.json    #   1.9 GB，约 100 万条对话
│
├── train/                        # 37 GB：分好词的训练数据
│   ├── shard_00000.bin           #   每片 1 亿 token × 4 字节 = 400 MB
│   └── ... shard_00099.bin       #   共 100 片
└── val.bin                       # 39 MB，约 1000 万 token 的验证集
```

**实测总量**（与 [AGENTS.md](../AGENTS.md) §1 一致）：

```
9.903B train + 0.010B val = 9.913B tokens
```

> ⚠️ 注意：**原始语料是 100 亿 token，训练只用了 50 亿**。
> 预训练跑 1 个 epoch 都不到（`--max_tokens 5000000000`），
> 剩下的数据是为「加练」留的余地。
> **这是刻意设计的** —— [run_pretrain.sh](../scripts/run_pretrain.sh) 顶部注释写着，
> 想加练只需把 `--max_tokens` 改成 0。

### 5.1 分片格式：裸 uint32 数组

`shard_00000.bin` **没有任何文件头、没有元数据、没有分隔符**，
就是 1 亿个连续的 32 位无符号整数（小端序）：

```
偏移 0    4    8    12  ...            400,000,000 字节
     ┌────┬────┬────┬────┬─ ... ─┬────┐
     │ 4  │120 │ 88 │ 998│       │  2 │   ← 每个 4 字节是一个 token id
     └────┴────┴────┴────┴─ ... ─┴────┘
      <|im_start|>  "The" ...
```

**为什么是这个格式**：

- **零解析开销**：`np.memmap(path, dtype=np.uint32)` 之后，取第 i 个 token 就是 `a[i]`
- **支持随机访问**：想做「从第 37 亿个 token 接着训」？直接 `a[3_700_000_000:]` 就行
- **操作系统帮忙缓存**：memmap 走页缓存，反复读同一片不会重复走磁盘

**代价：极其脆弱**。改一个字节，后面全部错位；文件大小不是 4 的倍数就是坏的。

**为什么用 uint32 而不是 uint16**：词表有 152,064 个 token，
超过 65535（uint16 上限），所以至少要 uint32。（如果用 uint16，
存储能省一半，但需要额外处理超出的部分。）

### 5.2 验证集是「最后 1 万篇文档」

[data_pretrain.py L107](../src/data_pretrain.py#L107)：

```python
val_start = n_rows - args.val_docs if (idx == len(files) - 1 and args.val_docs > 0) else None
```

从**最后一个 parquet 文件**的末尾取 1 万篇文档。

⚠️ **已知的不严谨之处**：这 1 万篇文档**同时也被写进了训练分片**，
即验证集和训练集有重叠。对「观察 loss 趋势」这个用途影响不大，
但严格来说应该做**文档级去重**。想改的话，把 `val_texts` 也写入
`train` 的路径改成 skip 即可。

## 6. 自己动手检查数据

### 6.1 分片里到底是什么文本

```python
import numpy as np
from tokenizers import Tokenizer

tok = Tokenizer.from_file("tokenizer/tokenizer.json")
a = np.memmap("data/train/shard_00000.bin", dtype=np.uint32, mode="r")

print("token 数:", a.size)                      # 期望 100,000,000
print("前 800 个 token 解码:")
print(tok.decode(a[:800].tolist()))
```

**期望看到**：一段通顺的英文（教育类内容，比如科普、教程）。
如果看到乱码或大量 `</s>`，说明编码或分片过程有问题。

### 6.2 文件大小是否对得上

```bash
ls -l data/train/shard_00000.bin
# 期望: 400000000  (100,000,000 × 4 字节)

du -sh data/train/
# 期望: 约 37G  (100 片 × 400MB ≈ 40GB，末片可能不满)
```

### 6.3 token 分布是否正常（进阶）

```python
import numpy as np
a = np.memmap("data/train/shard_00000.bin", dtype=np.uint32, mode="r")
sample = a[:10_000_000]
print("最大 id:", sample.max(), "(必须 < 152064)")
print("=</s> 的数量:", (sample == 2).sum(), "→ 文档数")
print("前 20 个最常见 id:", np.bincount(sample, minlength=152064).argsort()[-20:])
```

常见的**空格**、**逗号**、**the** 应该排在最前面。

### 6.4 原始数据看一眼

```python
import pyarrow.parquet as pq
pf = pq.ParquetFile("data/raw/000_00000.parquet")
print("行数:", pf.metadata.num_rows)
for batch in pf.iter_batches(batch_size=1, columns=["text"]):
    print(batch.column("text")[0].as_py()[:500])
    break
```

> 📌 注意这里用的是 `pq.ParquetFile` 而不是 `datasets`。
> [data_pretrain.py](../src/data_pretrain.py#L8) 的注释解释了原因：
> `datasets.map` 处理「长度不一的 list-of-lists」和 bytes 返回值时
> **会把一行展平成多行**，是个静默的数据损坏。
> `pyarrow.iter_batches` 是流式的、行为可预期的替代方案，
> 而且**内存峰值只有一个批次**（不用把 29 GB 全读进来）。

## 7. 数据相关的常见问题

| 问题 | 原因 / 处理 |
|---|---|
| `datasets` 下载卡住 / 报 `ConnectionError` | 你在直连 huggingface.co。设 `HF_ENDPOINT=https://hf-mirror.com` |
| `datasets` 报 parquet 解析错误 | 多半是断点续传交错写入导致的损坏（见 §3.2）。删掉重下 |
| `data_pretrain.py` 报「没有 parquet 文件」 | `--local_dir` 路径错了，或者下载还没完成 |
| 分片数不是 100 | 上次数到一半被打断了。用 `--skip_files N` 接着跑 |
| 训练时 `IndexError` / 数据看起来错位 | 分片损坏。删掉那一片重跑管线 |
| 磁盘满了 | `du -sh data/*` 看是谁占的；`data/raw/` 29 GB 理论上可删（但建议留着） |

**下载时间参考**（本项目实测，走 hf-mirror）：

- FineWeb-Edu 14 个 parquet（29 GB）：约 1~2 小时，取决于带宽
- GSM8K（2.7 MB）+ OpenHermes（1.9 GB）：几分钟

**分词时间参考**：`tokenizers` 的 Rust 批量编码约 **2.4M token/s**，
100 亿 token 大约 1~2 小时（受磁盘 IO 限制）。
